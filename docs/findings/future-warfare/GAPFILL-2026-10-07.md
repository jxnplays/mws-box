## Task 1 — Parse the `NXffs100` asset index; pull per-weapon stats

### 1.1 Outer container (confirmed by byte check)
- **[observed]** `E:\Call of Duty Future Warfare\NX1\code_pre_gfx_mp.ff`, bytes 0–7 =
  `4E 58 66 66 30 31 30 30` = `NXff0100`; bytes 8–11 = `00 00 01 65` (LE 0x165 = 357);
  bytes 38–45 = `4E 58 66 66 73 31 30 30` = `NXffs100`; bytes 46–47 = `00 00`; byte 48+ = high entropy.
  Header size = 38 bytes.
- **[observed]** SP files use `NXffu100` (`code_pre_gfx.ff` bytes 0–7), MP files use `NXff0100`.
- **[observed]** `NXffs100` occurs exactly **once** per MP fastfile, at a **variable** offset:
  `code_pre_gfx_mp.ff` @38, `ui_mp.ffm` @38, `development_mp.ffm` @38,
  `mp_nx_border_load.ff` @86, `common_mp.ffm` @41510, `mp_nx_shipyard.ff` @44006.
  (Scanned whole files, ASCII search, single hit each.)

### 1.2 The index is an offset table in the region BEFORE `NXffs100`
- **[observed]** `mp_nx_shipyard.ff` bytes 35–37 = `91 4B E6` = 0x914BE6 = 9522150, and
  bytes 39–41 = `91 4D 17` = 0x914D17 = 9522455 (3-byte big-endian pairs).
- **[observed]** `output/unpacked/mp_nx_shipyard/block_00914BE6.bin` **exists** — i.e. 0x914BE6 is a
  real zlib-block start offset. The pre-`NXffs100` table therefore indexes the compressed blocks.
- **[not in source]** A mapping from index entry → asset name. The index gives block offsets only;
  it does not carry damage/fire-rate fields.

### 1.3 Weapon NAMES located (no stats attached)
- **[observed]** `output/unpacked/code_post_gfx_mp/block_00004026.bin`, offset **4443129**, is a
  table of 16-byte records. 30 weapon-name records span 4443129–4443608:
  `scar, laserrifle, scar2, ecr, pulserifle, xm108, fal, asmk27, type104, ump45, p90, glo, rpd,
  m240, lasersniper, barrett, cheytac, m21, wa2000, cd2b, ksg, spas12, aa12, m1014, glock, beretta393,
  beretta, coltanaconda, ksgslug, warehouse1`.
  Each record is `name\0…` padded to 16 bytes (e.g. `asmk27` at 4443241, `type104` at 4443257).
- **[observed]** Offset 4443609 onward is a different table (`verb_rifle_sm_room_1`, `gallparking1`,
  floats `3F 40 00 00`=0.75, `3F 80 00 00`=1.0). It is a general string table, not a per-weapon stat array.
- **[observed]** `mp/statstable.csv` appears as a string at offset **4768384** in the same block,
  followed by 8-byte binary records (e.g. offset 4768406 = `30 12 D9 15 00 00 0B EF`). This could not be
  resolved to weapon stats without the NX1 weapon-def layout.

### 1.4 Per-weapon stat fields — result
